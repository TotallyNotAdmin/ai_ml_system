# Self Review

## Самая слабая часть решения

Самая слабая часть - упрощённые ML-компоненты:

- классификатор основан на правилах и ключевых словах;
- retrieval использует локальный TF-IDF-подобный подход;
- LLM заменён mock-клиентом;
- нет реальной оценки качества на исторических данных.

Это приемлемо для PoC, но не для production-запуска.

## Сделанные предположения

1. Автоматически можно закрывать только low-risk тикеты.
2. High-risk категории: платежи, безопасность, мошенничество, возвраты, персональные данные (PII).
3. LLM не должен участвовать в hot path.
4. При недоступности LLM безопаснее использовать шаблон или передавать оператору.
5. База знаний содержит только проверенные и безопасные формулировки.
6. Стоимость LLM можно контролировать дневным бюджетом.
7. Для PoC достаточно тестовых данных и локального запуска.

## Нерешённые риски

1. Возможность промпт-инъекции через пользовательский текст.
2. Ложное авто-закрытия тикета из-за плохой классификации.
3. Утечка персональных данных при недостаточно точной максировке.
4. Рост стоимости LLM при всплеске тикетов.
5. Деградация базы знаний.
6. Ошибки поиска, ведущие к неверному ответу.
7. Отсутствие реальной нагрузки и latency-тестов.

## Что можно улучшить за 2 дополнительных дня

1. Заменить правила на TF-IDF + логистическую регрессию.
2. Добавить больше тестовых тикетов и контрольную выборку.
3. Добавить структурированные метрики.
4. Добавить интерфейс (хотя бы консольный) для прогона оценки качества.
5. Улучшить обнаружение персональных данных: больше regex выражений и простые шаблоны распознавания именованных сущностей.
6. Добавить incident mode: дедупликацию похожих тикетов.

## Что нужно доработать перед production

1. Очереди и асинхронная обработка.
2. LLM gateway с таймаутом, повторными попытками и механизмом отключения при сбоях.
3. Полноценная БД для тикетов и журнала аудита.
4. Проверка подлинности, ограничение частоты запросов, управление секретами.
5. Наблюдение за системой и оповещения.
6. Оценка качества на сохранённых данных и поэтапное развертывание.
7. Интерфейс проверки ответов оператором.
8. Проверка обработки персональных данных и политик языковой модели.
9. Проверка на устойчивость к промпт-инъекциям и сценариям безопасности.
10. Нагрузочное тестирование на пиковые 10–20 тысяч обращений за 10 минут.

## Какие части системы не стоит автоматизировать полностью

Не стоит полностью автоматизировать:

1. Возвраты и компенсации.
2. Платёжные споры.
3. Подозрения на мошенничество.
4. Взлом аккаунтов.
5. Юридические запросы.
6. Жалобы с высоким эмоциональным риском.
7. Кейсы с персональными или чувствительными данными.
8. Инциденты с массовым сбоем до подтверждения статуса.

## Какие данные пилота убедили бы остановить проект

Я бы остановил или серьёзно пересмотрел проект, если бы:

1. Авто-закрытие тикета привело к сильному росту повторных открытий.
2. Оценка удовлетворённости по автоматическому закрытию упала ниже 3.8 или общая оценка удовлетворённости снизилась на 0.2 и более.
3. Обнаружились ошибочные автоответы в high-risk категориях.
4. Стоимость LLM превысила операционную экономию.
5. Появились подтверждённые случаи утечки персональных или чувствительных данных.
6. Операторы стали тратить больше времени на исправление ИИ-черновиков, чем на обычную обработку.
